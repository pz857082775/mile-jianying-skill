# 功能评测结论

> 评测对象：`mile-jianying-skill` v1.0.0（米乐-自动剪映视频）
> 评测日期：2026-10-29
> 评测方式：源码审查 + 单元测试 + 临时草稿端到端验证 + 真实草稿只读检查
> 安全约束：所有写入型测试均在系统 Temp 目录的草稿副本中完成，未修改 `src-tmp/` 参考源码，未改动用户真实草稿。
> 后续实测：真实剪映 5.9 端到端结果见 [real-jianying-5.9-e2e-report.md](real-jianying-5.9-e2e-report.md)（2026-10-29）。

---

## 1. 结论摘要

这个项目在二次开发前，本质是一组围绕 `pyJianYingDraft` 的**能力演示脚本集合**：能生成草稿、加素材、加字幕、加特效，也能调用一些非官方云端能力，但缺少统一的编辑协议、可回滚的事务、对已有草稿的精准修改，以及跨会话的经验沉淀。

v1.0.0 新增的 `scripts/mile/` 确定性编辑层改变了这一点。它把「改一个已有草稿」拆成五个稳定步骤：

1. `timeline`：把 `draft_content.json` 解释成带语义的片段模型；
2. `find`：按 ref / 轨道 / 时间 / 文字 / 角色 / 素材类型定位目标；
3. `edit` 或 `plan`：只对目标片段执行操作，计划全部校验通过才落盘；
4. `qa`：对成片做结构与一致性体检，可安全自动修复；
5. `memory`：记录本次需求、操作、结构与风格，供下次同类视频召回。

因此，**它已经具备"自然语言 → 结构化计划 → 精准片段修改 → 质检 → 记忆"的 Agent 剪辑骨架**，但自然语言理解本身仍由上层 Agent 完成，项目提供的是可靠执行层，而不是内置大模型。

> **2026-10-29 智能层第一版更新**：本报告的评测对象是确定性编辑层基线。此后新增的 `smart` / `subtitles` / `recommend`（`scripts/mile/intent.py`、`subtitles.py`、`recommend.py`、`smart.py`）已在项目内补上**规则/槽位型中文指令翻译层**与字幕整理、BGM/转场推荐，详见 [improvement-plan.md](improvement-plan.md) 的「阶段 P0.4」。它不是大模型语义理解：复杂或歧义指令仍需上层 Agent 或 `edit`/`plan` 精确表达，因此下文的「语义理解仍需调用方补齐」在长尾表达上依然成立。

一句话评价：

> **执行力强、边界清楚、可回滚、可积累经验；语义理解和创意判断仍需调用方（Agent/人）补齐。**

## 2. 架构与模块划分

### 2.1 分层结构

```text
用户自然语言
    │
    ▼
上层 Agent（Qoder / Claude / 其他）
    │  拆解需求、选择命令、生成计划 JSON
    ▼
┌─────────────────────────────────────────────────────┐
│ 统一 CLI：scripts/mile_cli.py                        │
│ version / doctor / drafts / timeline / find / plan   │
│ apply / edit / qa / undo / backups / srt / export    │
│ assemble / memory                                    │
└─────────────────────────────────────────────────────┘
    │
    ├── 确定性编辑核心 scripts/mile/
    │     timecode  时间解析（秒/毫秒/时钟/中文单位 → 微秒）
    │     draft     草稿定位、原子保存、备份、撤销
    │     timeline  轨道/片段语义建模（ref、role、字幕/主轨/BGM）
    │     ops       16 种片段级操作
    │     plan      计划校验 + 事务化应用 + 失败回滚
    │     quality   结构与一致性检查 + 安全修复
    │     memory    剪辑记忆：记录、去重、召回、反馈、遗忘
    │     assemble  按素材/字幕/BGM/历史风格组装草稿
    │
    └── 高层生成 API scripts/jy_wrapper.py + scripts/core/
          project_base  生命周期、路径安全、时间轴审计
          media_ops     视频/音频/云端素材导入与轨道分层
          text_ops      字幕、花字、TTS 旁白
          vfx_ops       特效、转场、贴纸、网页动效
          mocking_ops   云素材补丁、花字资源路径、调色激活
    │
    ▼
剪映草稿目录 draft_content.json / draft_meta_info.json
```

### 2.2 规模

| 分组 | 文件数 | 代码行数（约） |
|---|---:|---:|
| CLI + 确定性编辑核心 | 11 | 5,400 |
| 高层封装（JyProject / core） | 8 | 2,500 |
| 媒体、云端、AI、导出等工具 | 18 | 4,300 |
| 录屏工具 | 2 | 900 |
| 测试 | 4 | 1,200 |

### 2.3 关键设计

- **秒进微秒出**：对外 API 和文档统一用秒（`2s`、`1m2.5s`、`00:01:30`），内部统一微秒，避免单位混用。
- **引用定位**：每个片段生成稳定 `ref`（id 前缀），编辑不依赖易变的下标。
- **事务化**：`plan` 先全量校验；`apply` 任一操作失败即回滚内存修改，不落半套编辑。
- **默认备份**：每次保存前写入 `.mile_backups/`，`undo` 可恢复最近一次。
- **语义轨道角色**：识别 main / broll / caption / title / bgm / voice / pip，支持按角色批量操作。
- **记忆指纹**：草稿结构签名 + 风格摘要 + 文本 bigram，同项目 30 分钟内去重合并。

### 3.1 草稿发现与时间轴读取

**效果**

- `drafts` 能列出草稿并可选附带时长、画布摘要。
- `timeline` 输出轨道、片段、角色、时长、间隙与重叠统计。
- 片段 `ref` 为 id 前缀，便于后续稳定定位。

**优点**

- 只读解析，不触碰素材与草稿内容。
- 对 `flag`、`role` 的解释贴近剪映真实语义（主轨 / 画中画 / 自动字幕 / 普通文本）。
- 支持 `--full` 输出完整字段，便于上层 Agent 做复杂决策。

**缺点 / 局限**

- 时间轴模型是「只读投影」，不会自动修复异常字段；异常数据要到 `qa` 才暴露。
- 轨道编号中 `video#1` 是第 1 条视频轨（1 基），而片段 `index` 是轨道内序号（0 基）；两种编号并存，初次使用需要看文档。

**结论**：作为 Agent 的「眼睛」足够可靠，是精准编辑的前提。

---

### 3.2 精准片段编辑

**效果**

端到端验证过的链路：

```bash
find "Smoke" --track "video#1" --index 0
# → 命中 1 个片段：3BB3FA30

edit "Smoke" --op trim \
  --target '{"track":"video#1","index":0}' \
  --param end=1.5s --param ripple=true
# → 片段 0-2s 裁到 0-1.5s，后续片段前移，总时长 4s → 3.5s
```

`qa` 随后返回 0 error / 0 warning，声明时长与实际时长一致。

**优点**

- 16 种操作覆盖高频需求：delete / trim / move / shift / split / set_text / set_volume / set_speed / set_transform / set_visible / set_canvas / add_transition / remove_transition / clone_text / add_text / add_audio。
- 定位器组合灵活：ref、多个 ids、轨道、轨道内序号、时间范围、时间点、文字包含、素材名、角色、素材类型、时长上下限。
- 默认按「只改目标片段」执行；`ripple` 控制后续片段是否跟随。
- 转场语义正确：挂在前一个片段，且校验后一个片段同轨相邻。

**缺点 / 局限**

- 操作粒度是「片段级」，不是「帧级」；无法直接做逐帧微调、曲线变速、蒙版路径编辑。
- 变速、裁剪、音量等操作会同步修正 `source_timerange`，但复杂多轨联动（例如同时移动字幕 + BGM）需要计划里逐步描述。
- 对剪映新增的未知片段类型，`ops` 只保证不破坏未知字段，不保证能解释其语义。

**结论**：这是 v1.0.0 最有价值的能力，直接回应了「对特定片段下达精准优化指令」。

### 3.3 结构化计划与回滚

**效果**

以下 3 步计划一次性通过校验并应用：

```json
{
  "intent": "加标题并统一节奏",
  "tags": ["冒烟", "字幕"],
  "ops": [
    {"op": "add_text", "text": "冒烟标题", "start": "0s", "duration": "2s"},
    {"op": "set_speed", "target": {"track": "video#1", "index": 0}, "speed": 1.2},
    {"op": "set_volume", "target": {"track": "video#1", "index": 0}, "volume": 0.5}
  ]
}
```

`plan` 返回 3 条 operation；`apply` 三条全部 `applied`；`qa` 通过。

**优点**

- 计划是自然语言与草稿之间的可审计中间层：可以先给用户看「准备做什么」，再执行。
- 支持中文 op 别名（删除 / 裁剪 / 变速 / 改文字 / 加字幕 …）。
- 失败回滚有测试保障，避免半套编辑。
- `--dry-run` 可只校验不落盘。

**缺点 / 局限**

- 计划格式仍偏底层：要求上层 Agent 自己把「把第 28 秒那个转场去掉」翻译成 selector + op。
- 没有内置的「计划解释器」把自然语言直接变成计划；这属于规划中的 `intent` 层。
- 跨草稿的批量计划（同时对 10 个草稿执行）尚未支持。

**结论**：可靠执行层已具备，缺少的只是更聪明的「翻译层」。

### 3.4 质量检查与修复

**效果**

`qa` 对临时草稿返回：

```json
{"summary": {"error": 0, "warning": 0, "info": 0}, "ok": true,
 "declared_duration": 3500000, "actual_duration": 3500000}
```

**覆盖的问题码**（17 类）

- 结构：`NO_MAIN_TRACK`、`TRACK_OVERLAP`、`MAIN_TRACK_GAP`、`SEGMENT_NEGATIVE_START`、`SEGMENT_ZERO_DURATION`
- 素材：`MATERIAL_MISSING`、`MEDIA_FILE_MISSING`、`EXTRA_MATERIAL_MISSING`、`DRAFT_DURATION_MISMATCH`
- 文本：`TEXT_EMPTY`、`TEXT_TOO_SHORT`、`DUPLICATE_TEXT`、`SUBTITLE_GAP`
- 参数：`SPEED_OUT_OF_RANGE`、`AUDIO_VOLUME_HIGH`、`FPS_INVALID`、`CANVAS_ODD`

**优点**

- 默认只读；`--fix` 才修改，且保存前自动备份。
- 检查的是「剪映会真实出问题」的结构：缺主轨、轨道重叠、素材丢失、字幕越界、时长声明不一致。
- 错误码稳定，适合 Agent 做自动重试或提示。

**缺点 / 局限**

- 不检查画面质量：黑帧、静音、口型不同步、字幕溢出画面、响度超标等需要媒体分析。
- `SUBTITLE_GAP` 等规则是启发式，可能对刻意留白产生 info 级噪音。
- 修复策略偏保守，不能自动重排复杂时间线。

**结论**：作为「保存前最后一道闸门」合格；作为「成片艺术质量评估」还差得远。

### 3.5 剪辑记忆

**效果**

- `assemble` / `edit` / `apply` 默认写入记忆，记录需求、标签、操作、草稿指纹、结构签名、风格摘要、结果与自评分。
- 同指纹 30 分钟内去重合并，避免反复保存刷屏。
- `memory --action recall --intent "..."` 返回相似历史、Top-K 风格与建议。
- `memory --action feedback` 记录评分与结果；`forget` 可删除。

**评分权重**（`scripts/mile/memory.py`）

- 有文本查询：文本 0.40 + 结构 0.25 + 风格 0.15 + 时效 0.20
- 仅草稿参考：结构 0.45 + 风格 0.25 + 时效 0.30

**优点**

- 记忆是「结构化经验」而不是聊天记录：字号、颜色、转场、BGM、镜头节奏、切点密度都可复用。
- 反馈闭环可以强化有效经验、弱化被拒绝的风格。
- 本地 JSONL 存储，无云依赖，可读可导出。

**缺点 / 局限**

- 文本相似度是 bigram Jaccard，不理解同义词和语义；「科技产品」与「数码新品」可能匹配不上。
- 风格合并是统计式（众数/中位数），无法表达「这条视频要刻意反常规」。
- 目前没有项目/系列命名空间，长期使用后需要靠 tag 和 project 过滤。
- 没有记忆可视化与手动编辑入口（只能 list / forget）。

**结论**：记忆骨架可用，是本项目区别于普通剪辑脚本的核心差异；下一步应从「词法记忆」升级为「语义 + 偏好记忆」。

### 3.6 智能组装

**效果**

```bash
assemble assets/video.mp4 assets/video.mp4 \
  --project Smoke --width 1080 --height 1920 \
  --clip-duration 2s --transition 叠化 --transition-duration 0.4s
```

返回 2 段、4 秒、竖屏草稿，`qa` 通过，并自动写入记忆。

**优点**

- 给定素材、字幕、BGM、转场即可生成可继续精修的草稿。
- 可读取历史风格（字号、颜色、字幕位置、BGM 音量、转场习惯）。
- 支持 `--style` 内联覆盖与 `--no-memory-style` 关闭。
- 图片素材默认 3 秒，无 ffprobe 时可用 `--clip-duration` 兜底。

**缺点 / 局限**

- 镜头排序是「输入顺序」，没有内容理解；不会自动判断哪段适合开场。
- 转场只支持统一一种，不能按镜头内容差异化。
- 字幕时间轴依赖 SRT/JSON，不能自动语音转写。
- BGM 只做整体音量，没有 ducking、卡点、段落情绪匹配。

**结论**：合格的「底稿生成器」，不是「自动导演」。

### 3.7 高层生成 API

**E2E 验证**

- **花字**：`add_styled_text` 在 `add_segment` 之前调用 `add_effect`，`effectStyle` 正确写入，资源复制到 `<draft>/Resources/artistEffect/...`。
- **贴纸**：`add_sticker_at` 使用 photo 素材 + ClipSettings，成功生成独立视频轨片段。
- **画中画变换**：`add_media_safe(..., transform_y=0.2, scale=0.4)` 现在真正写入 `ClipSettings`，序列化后 `clip` 字段为 `scale {x:0.4,y:0.4}`、`transform {y:0.2}`。
- **测试**：50 个用例全部通过。

**优点**

- 把 pyJianYingDraft 的严格校验和路径问题封装掉，失败时返回 `None` 而不是崩溃。
- 时间参数支持 `"1m2.5s"`、`"00:01:30"`、毫秒、微秒。
- 自动处理素材缺失、WEBM 转码、音频轨道重叠分层。
- 文本/花字/贴纸/转场/特效/云端素材/网页动效入口齐全。

**缺点 / 局限**

- 高层 API 仍以「生成新内容」为主，不适合逐片段修改已有草稿（那是 `mile` 层的工作）。
- 依赖 `pyJianYingDraft` 的内部 JSON 结构，剪映大版本升级可能失效。
- 无 ffprobe/pymediainfo 时必须显式给时长，否则底层无法解析素材。
- 复合片段（Compound Clip）没有可靠接口，示例已改为诚实的画中画叠加方案。

**结论**：生成能力完整，适合「从零搭草稿」；修改已有草稿请走 `mile_cli.py`。

### 3.8 云端素材、AI 文案与 TTS

**能力**

- `cloud_manager`：本地 CSV 素材库检索、下载缓存、SSRF 防护、大小限制。
- `jianying_ai_writer`：通过剪映 Frontier WebSocket 生成文案（非官方协议）。
- `universal_tts`：优先剪映 SAMI TTS，回退 edge-tts，支持语速调整。
- `asset_search`：同义词扩展的素材检索。

**优点**

- 素材下载有安全边界：阻断 localhost/私网、HTML 响应、超大文件。
- 文案与配音可直接接入 `add_ai_voiceover` / `add_narrated_subtitles`。
- TTS 有双通道回退，避免单点故障。

**缺点 / 局限**

- 非官方接口：协议、鉴权、模型名可能随剪映版本变化，不适合作为长期稳定依赖。
- 需要本机剪映配置/设备 ID；在无剪映或网络受限环境不可用。
- 本环境缺 `edge_tts`、`websockets` 可用但未做真实合成测试；文档已标注为可选依赖。
- 生成内容没有事实校验，文案质量取决于外部模型。

**结论**：适合作为「增强能力」，不应作为核心剪辑链路的前置依赖。

---

### 3.9 视频分析与智能粗剪

**能力**

- `video_analyzer`：ffmpeg 抽帧、场景变化检测、字幕匹配画面。
- `smart_rough_cut`：按场景切分，生成粗剪草稿。
- `movie_commentary_builder`：按故事板 JSON 切片、字幕遮罩、双轨原声增强。

**优点**

- 设计思路正确：先场景检测，再按时长/数量挑选片段，最后组装。
- 已移除对不存在的 `AntigravityClient` 的依赖，改为本地分析。
- 修复了无文本场景重复添加 HighlightTrack 片段的问题。

**缺点 / 局限**

- 强依赖 ffmpeg / numpy / OpenCV，本机未安装 ffmpeg，无法端到端验证。
- 场景检测基于帧差阈值，对渐变、运镜、光线变化敏感；不是语义理解。
- 高光识别、语音转写、情绪曲线尚未实现。
- 长视频处理耗时，缺少 GPU 加速与断点续跑。

**结论**：有「粗剪」雏形，但离「智能导演」还有明显距离。

### 3.10 录屏与智能缩放

**效果**

用合成事件 JSON 驱动 `apply-zoom`：

- 3 次点击被分为 2 个缩放 session；
- 生成 `KFTypeScaleX` / `KFTypePositionX` / `KFTypePositionY` 关键帧；
- 缩放 1.0 → 1.5 → 停留 → 恢复；
- 点击位置生成 0.5 秒红点标记；
- 无 ffprobe 时按事件最晚时间 +1s 推断视频时长，成功导入。

**优点**

- 从录屏到「可看的演示视频」路径最短。
- 坐标归一化，缩放位置不依赖分辨率。
- 红点标记让观众知道操作位置。
- 缩放带回弹和边界钳制，避免黑边。

**缺点 / 局限**

- Windows 录制器依赖 `pynput`、`tkinter`、ffmpeg；macOS 录制器需自行安装 ffmpeg。
- 自动导出仅支持剪映 5.9 及以下（上游限制）。
- 事件坐标为归一化值；外部自造事件需遵守该约定。
- 长录屏 + 大量点击会生成大量关键帧，时间轴较重。

**结论**：产品演示、软件教学场景可直接用；复杂运镜仍需手工。

### 3.11 Web 动效录制

**能力**

- `web_recorder.py` 用 Playwright 打开本地 HTML/URL，等待 `window.animationFinished` 信号后停止录制。
- 请求 MP4 时用 ffmpeg 转码；无 ffmpeg 时降级保存 `.webm` 并明确警告。
- 修复了 GBK 控制台 import 阶段打印 emoji 导致 `UnicodeEncodeError` 的问题。

**优点**

- 用「动画结束信号」而不是固定 sleep，录制时长准确。
- 转码与降级路径清晰，不会假装成功。

**缺点 / 局限**

- 依赖 Playwright 浏览器与 ffmpeg，安装成本高。
- 只适合网页动效，不适合真实桌面操作。
- 无声音采集。

**结论**：细分场景工具，可用但非核心。

### 3.12 自动导出

**能力**

- `auto_exporter.py` / `mile_cli.py export`：调用 pyJianYingDraft 的剪映控制器导出 MP4。
- `windows_export_agent.py`：Windows 端 HTTP 服务，供 macOS/远程触发导出。
- 支持 480P–8K、24–60fps，参数已做 `1080`/`1080P`、`30`/`30fps` 归一化。

**优点**

- 导出参数完整，远程 Agent 设计合理。
- JSON body 与 query 双解析，任务先注册再启动，避免竞态。

**缺点 / 局限**

- 依赖 uiautomation、剪映客户端、固定 UI 布局和版本（5.9 以下）。
- 本环境未安装 uiautomation，无法实测。
- macOS 自动导出不可用，只能手动导出。
- 剪映升级后 UI 选择器可能失效，属于高风险外部依赖。

**结论**：能用但不稳，建议始终保留「手动导出」兜底。

### 3.13 兼容性与安全

**做得好的地方**

- `_safe_join_root` 阻止 `..` 越界；项目名安全化。
- 云下载阻断 localhost/私网、HTML/JSON 响应、超大文件。
- 保存时保留未知字段，不做「白名单重建」，降低破坏剪映新特性的风险。
- 默认备份 + 可撤销。
- 测试全部在临时目录，遵守「不碰真实草稿」。

**风险点**

- 依赖非官方 JSON 结构与 UI 自动化，剪映升级是最大系统性风险。
- 记忆库目前是本地明文 JSONL，若记录敏感项目信息需用户自行管理。
- 云端素材下载会把文件落到工作区 `cloud_cache/`，需注意版权与磁盘占用。

## 5. 总体评价

### 优势

1. **执行可靠**：定位、修改、回滚、备份、质检形成闭环。
2. **边界诚实**：不宣称能做复合片段，不假装无 ffprobe 也能探测时长，失败会明确报错。
3. **可积累**：记忆让「同类视频越剪越顺手」成为可能。
4. **Agent 友好**：JSON 信封、稳定错误码、结构化计划，适合被大模型调用。
5. **文档完整**：SKILL、Playbook、SOP、14 份 rules，降低上层 Agent 的使用门槛。

### 主要短板

1. **没有内置大模型语义理解**：自然语言 → 计划已有规则/槽位翻译层（`smart`，第一版），但只覆盖高频说法，长尾表达与真正歧义仍需上层 Agent 或 `edit`/`plan` 精确指定。
2. **记忆偏词法**：同义词、跨项目风格迁移、负反馈学习还不够深。
3. **媒体智能浅**：ASR 只有可选 faster-whisper 接入位（缺失即 `ASR_UNAVAILABLE`，不伪造字幕）；BGM/转场推荐基于音频信号与曲库元数据，不是内容理解；高光识别、卡点、自动重构比例仍缺。
4. **导出链路脆**：强依赖剪映版本与 UI 自动化。
5. **无批量/多版本能力**：矩阵号运营场景还缺一条流水线。

### 适用场景

- ✅ 已有剪映草稿的精准修改（改字幕、调节奏、换转场、删片段）。
- ✅ 口播/知识类视频的结构化组装与字幕对齐。
- ✅ 产品演示录屏的自动缩放与标记。
- ✅ 需要「可回滚、可审计」的自动剪辑流水线。
- ⚠️ 从零生成高质量成片：需要外部文案、TTS、素材与人工审美。
- ❌ 专业级调色、复杂特效、逐帧精修：请回剪映/PR/达芬奇。
